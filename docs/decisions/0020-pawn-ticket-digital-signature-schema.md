# Decision 0020 — Pawn Ticket Digital Signature — Schema Additions

**Date:** 2026-06-10
**Epic:** E107 — Pawn Ticket Generation & Digital Signature (POS)
**Status:** Planned — schema extended ahead of E107 execution

## Decision

Extended `loanTickets/{id}` with five new fields to support in-store POS signature capture
and printed ticket issuance. Also added `pawn_agreement_signed` to the `auditLogs.eventType`
closed enum.

## Fields Added to `loanTickets/{id}`

| Field | Type | Rationale |
|---|---|---|
| `ticketNumber` | string | Human-readable reference for the printed ticket (e.g. `PLT-20260610-A3F2`). Generated by `createLoanTicket` CF using date + doc-id prefix. Staff and customer reference this when redeeming. |
| `signatureUrl` | string \| null | Firebase Storage URL of the customer's signature PNG. Null until signed via `signPawnAgreement` CF. |
| `signedAt` | timestamp \| null | Server timestamp at moment of signing — compliance audit anchor. |
| `agreementVersion` | string \| null | Version slug of the agreement template shown (e.g. `'v1.0'`). Enables re-consent detection if terms change. |
| `customerName` | string | Customer's full name at time of signing, stored for agreement document validity (same pattern as `reservations.customerName`). Never in `auditLogs`. |

## Why These Fields on the Document (Not a Subcollection)

Signature metadata is operationally load-bearing: staff need to see whether a ticket has
been signed without an extra Firestore read. Putting it on the root document avoids an
N+1 read in the `LoanTicketsAdminPage` list view.

The signature image itself lives in Firebase Storage (not Firestore) — keeping Firestore
documents lean and Storage costs predictable.

## `auditLogs.eventType` Addition

Added `pawn_agreement_signed` to the closed enum. Event payload:
```
{ loanTicketId: string, agreementVersion: string }
```
No PII in details — customer identity is recoverable from `loanTickets/{id}.uid`.
